# Recording processing latency

Worker logs emit `call_processing.stage_started`, `call_processing.stage_completed`, and `call_processing.stage_failed` for download, normalization, transcription, scoring, and persistence. Version 2 jobs also time audio chunking; legacy jobs include any chunking inside transcription. Each event has `jobId`, `callId`, `generation`, `attemptCount`, `stage`, and `startedAt`. Completion and failure events add `completedAt` and `elapsedMs`. Events contain no transcript or provider error text.

Find all events for one `jobId` in the worker logs and group by `generation` and `attemptCount`. Do not sum profile and score durations: they run concurrently after transcription. Existing `call_processing.chunk_*` events provide chunk counts, sizes, retries, and provider time for version 2 jobs. A checkpointed retry may skip download or transcription entirely; absence of those stages on that attempt is not zero latency.

`call_processing_jobs.created_at` is the earliest database timestamp for a queued job. `locked_at` is the latest claim timestamp, and `processing_started_at` is the first processing start for version 2. Compare these to stage starts to identify queue delay. The new stage events live in worker logs, not in a database timing table; retain/export logs before their configured retention expires. Media upload or provider recording availability happens before job creation and must be measured separately.

For a controlled benchmark, upload the same rights-cleared synthetic audio to Argos and HTSA three times at each chosen length. Record upload start/acceptance, transcript visible, score visible, audio duration/bytes/codec, and rubric quality. Separate upload and provider recording availability from application processing. Do not infer HTSA's server provider or exact latency from its completed-call list. Compare speed alongside transcript accuracy, speaker attribution, scoring evidence, and cost before changing models or concurrency.
